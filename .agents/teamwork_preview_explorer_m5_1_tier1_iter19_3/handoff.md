# Handoff Report — Milestone 5.1 (Tier 1 E2E Test Pass - Feature Coverage)

## 1. Observation
- **Teardown Race Condition & Split-Brain Container State**: In `e2e/run_e2e.ts`, the existing teardown sequence executes `pkill -9 -f "supabase"` before `npx supabase stop --no-backup`. When `pkill` terminates the Supabase CLI process while it is actively spinning up Docker containers, the Docker daemon continues starting containers asynchronously in the background. When `docker ps -aq | xargs -r docker rm -f` runs, it sees an empty container list at that exact millisecond and exits. Subsequently, the Docker daemon finishes starting the remaining containers and writes `supabase/.temp/status.json`. When `npx supabase start --ignore-health-check` runs, it sees `status.json`, prints `supabase start is already running`, and exits immediately with 0 without starting the database container or running migrations, resulting in `relation "public.expenses" does not exist` during `init_db.ts`.
- **Unprotected `cleanup()` Teardown**: `e2e/run_e2e.ts` lines 118-124 use a legacy teardown sequence (`npx supabase stop` followed immediately by `docker volume rm -f`), causing `a prune operation is already running` errors.
- **Cascading Teardown Collisions in Health Check Loops**: In `e2e/run_e2e.ts`, health check loops poll `http://127.0.0.1:54321` every 2 seconds (`await new Promise(resolve => setTimeout(resolve, 2000))`). When Supabase is unresponsive, at retries 15, 10, and 5, the script executes the teardown block and invokes `npx supabase start --ignore-health-check`. Because Supabase takes >10s to boot, 5 retries elapse in 10 seconds, causing the loop to trigger the next restart threshold while `npx supabase start` is still initializing containers in the background, causing container thrashing (`TypeError: fetch failed`) and cascading teardown collisions (`supabase start is already running`).
- **Flawed Health Check Assumption**: `e2e/run_e2e.ts` verifies readiness by polling `http://127.0.0.1:54321` (Kong API Gateway). Because Kong initializes rapidly and responds with HTTP 200/400/404, `e2e/run_e2e.ts` incorrectly concludes that the entire Supabase stack is healthy. In reality, the underlying Postgres database container (`supabase_db_expense-dashboard`) takes longer to initialize. When `npx supabase migration up` runs, Postgres is not ready, causing `LegacyDbConnectError: failed to connect to postgres`. Furthermore, `supabase_pooler` exits because it cannot reach the DB (`nxdomain`), causing the fallback `npx supabase db reset` to fail with `supabase start is not running`.

## 2. Logic Chain
1. **Reordering Teardown Sequence**: By executing `npx supabase stop --no-backup` and Docker container/volume removal BEFORE `pkill -9 -f "supabase"`, and removing `supabase/.temp` at the very end of the teardown block, we eliminate the Docker daemon race condition and prevent lingering `status.json` files from aborting `npx supabase start`.
2. **Standardizing Teardown Across All 7 Locations**: Applying the exact reordered bulletproof teardown sequence across `setup()` initial cleanup, `setup()` loop start, `setup()` loop catch block, `run()` health check recovery, `run()` pre-seed health check recovery, `run()` post-build health check recovery, AND `cleanup()` ensures no legacy teardown can trigger `a prune operation is already running`.
3. **Eliminating Cascading Restart Collisions**: Increasing the health check polling interval from `2000` ms to `5000` ms and adding a post-start stabilization delay (`sleep 20`) after `npx supabase start --ignore-health-check` in all recovery blocks provides ample time for Supabase containers to fully initialize before the loop resumes checking.
4. **Explicit Postgres Readiness Verification**: Importing `Client` from `pg` and explicitly verifying Postgres database readiness at port `25432` (in addition to `http://127.0.0.1:54321`) guarantees that `npx supabase migration up --include-all` only runs when Postgres is fully ready, eliminating `LegacyDbConnectError`. Replacing `npx supabase db reset` in the catch block with a full `npx supabase stop` and `npx supabase start` ensures clean recovery from any transient migration failures.
