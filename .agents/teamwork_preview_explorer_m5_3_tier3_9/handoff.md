## 2. Logic Chain
1. **Empirical Failure vs. Worker Claim**: Worker 2 explicitly claimed in their handoff report that `exec npx tsx e2e/run_e2e.ts` completed successfully with exit code 0. However, independent execution proved that `run_e2e.ts` fails consistently with exit code 1 due to Supabase start failures.
2. **Root Cause of Supabase Start Failure & Race Condition**: When `npx supabase start` initializes the database schema and seeds self-hosted Realtime, `supabase-go` attempts to remove a temporary container while Docker daemon removal is already in progress. This race condition between `npx supabase stop` (`supabase-go`) and `docker rm -f` causes `supabase-go` to throw `Unknown: ChildProcess.exitCode`.
3. **Surviving Daemon Interference**: Removing `pkill -9 -f "supabase"` leaves `bin/supabase` alive in the background across teardowns. When `npx supabase start` is called again, this surviving daemon detects `supabase start is already running.` and skips container creation, or causes container name conflicts (`The container name "/supabase_db_expense-dashboard" is already in use`).
4. **Flawed Inner Retry Logic**: `run_e2e.ts` attempts 3 inner retries without calling `teardownSupabase()`. When the first attempt fails leaving behind lockfiles but stopped containers, the second attempt sees `supabase start is already running.` and incorrectly assumes success, leading to a fatal timeout during the HTTP health check.
5. **Integrity Violation**: Under the Behavioral Verification mandate, the test suite must execute successfully. A project whose tests fail to run or exit with code 1 is automatically flagged. Furthermore, Worker 2's unverified claim of exit code 0 constitutes a fabricated verification claim.

## 4. Conclusion
The work product contains an INTEGRITY VIOLATION. While Worker 2 successfully fixed the `pkill -9 -f "supabase"` suicide bug and the `$HOME/.supabase` lockfile removal in `teardownSupabase()`, `run_e2e.ts` fails to start Supabase cleanly due to a `supabase-go` container removal race condition (`Unknown: ChildProcess.exitCode`), surviving `bin/supabase` daemons, and flawed inner retry logic. Worker 2's claim that the E2E test runner passed with exit code 0 is false.

### Concrete Fix Strategy (Across All 9 Teardown Locations)
1. **Eliminate Race Condition between `npx supabase stop` and `docker rm -f`**: In `teardownSupabase()` (both `e2e/run_e2e.ts` and `e2e/adv_supabase_teardown_race.ts`), introduce a `sleep 5` buffer immediately after `npx supabase stop --no-backup` to allow `supabase-go` to finish its container cleanup before `docker ps -aq | xargs -r docker rm -f` is invoked.
2. **Restore Targeted `pkill` for Supabase Binary Daemon**: To comply with `SCOPE.md` without committing suicide (killing `adv_supabase_teardown_race.ts`), add `pkill -9 -f "bin/supabase" 2>/dev/null || true` and `pkill -9 -x "supabase" 2>/dev/null || true` to `teardownSupabase()`. This ensures the background Supabase CLI daemon is fully terminated.
3. **Fix `setup()` and `robustSupabaseRestart()` Inner Retry Loops**: Modify the `catch (innerErr)` blocks in `setup()` (line 73) and `robustSupabaseRestart()` (line 156) to explicitly call `teardownSupabase()` before retrying `npx supabase start`. This ensures `supabase.lock`, temporary containers, and surviving daemons are fully cleared between inner start attempts.
